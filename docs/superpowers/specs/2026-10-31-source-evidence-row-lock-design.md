# Disposable authority row-lock design

Continue the owner evidence prototype with plain authority writers that do not acquire a global advisory lock or install provider Auth triggers. Keep the existing evidence metadata advisory lock. Before it, lock exact account, session, singleton Admin and singleton feature rows in that order FOR SHARE, then perform the unchanged runtime/Admin/current feature checks. READ COMMITTED only; missing rows fail closed. No claim about a provider schema or real Auth deployment.

Approaches: the previous global trigger fixture works only with cooperating writers; a separate revocation ledger adds new freshness/authority obligations; representative row locking can conflict with ordinary SQL updates/deletes directly. Test the last approach without treating it as a production approval. FOR KEY SHARE is deliberately tested as an unsafe negative control for non-key suspension/feature updates.

Use a separate non-login/non-bypass evidence_authority_locker owner for one private empty-search-path SECURITY DEFINER lock-only function, callable only by the existing executor. Grant only required schema usage, SELECT columns and minimal UPDATE-column privileges PostgreSQL requires to take row locks. Add SELECT RLS policies and UPDATE USING(true) WITH CHECK(false) for locking visibility while rejecting every actual UPDATE; no function writes Auth. Gateway and executor do not get direct Auth table/update access or locker membership. Existing runtime/Admin SQL is unchanged.

Native proof: real narrow login clients, writer-first session deletion/account suspension/deletion flag/Admin/feature changes, stage-first versions, rollback/retry with no orphan evidence, deterministic mixed-lock-order deadlock detection and transaction rollback/reconciliation. Observe real blocking PIDs and tuple/transaction locks, not sleeps or advisory-only barriers. Establish no synthetic Auth mutation triggers and exact locker ACL/catalog shape. Use separate administrator writer connection as before; no provider least-privilege writer integration is claimed.

Non-goals: real migrations/roles/credentials/routes, provider session expiry/refresh/MFA/cleanup behavior, all-provider deadlock freedom, hardware durability, source rights/reviewer/learner release. Row locks persist through the enclosing transaction, so keep transactions short and bound waits. A detected deadlock/unknown acknowledgement returns no accepted receipt; reconcile the same request. Gateway direct SQL can still impersonate through trusted actor/session delegation.

Ruling: local positive probe showed row locking also needs UPDATE-policy USING visibility. Add USING(true) WITH CHECK(false), with actual UPDATE rejection regressions; merely omitting UPDATE policies returns no lockable rows.
