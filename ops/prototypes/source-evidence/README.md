# Disposable source-evidence SQL prototype

**NOT A MIGRATION. Never apply schema.sql to a hosted database or expose evidence_probe.** The standalone script creates a new in-memory PGlite instance, uses synthetic owners/policies/claims and closes it in finally. It has no URL, credentials or hosted-database option. No app dependency is added.

Run with an externally installed pinned PGlite package (tested 0.5.13):

```sh
PGLITE_MODULE_URL=file:///absolute/scratch/tooling/node_modules/@electric-sql/pglite/dist/index.js node scripts/source-evidence-db-check.js
```

The prototype stages canonical package/manifest bytes, per-case JSON projections, actor-scoped request receipts and events in one SQL function transaction. SQL verifies manifest and receipt-payload byte hashes and binding consistency. Existing JavaScript strict/JCS preparation is mandatory before this trusted server-only call; The supplemental digests.sql now independently derives case/appearance/manifest/request/receipt hashes for the restricted metadata domain and checks canonical supplied bytes. The script independently rehashes stored claims and resolves a selected mixed-source case after a separate readback. SQL returns **committed**, never accepted; this is not the final staging adapter.

Checks exercise exact receipt retry; changed request/same revision conflict; exact older revision read after a new version; wrong version/digest/actor denial, including a second enabled owner attempting existing revisions, retries and new versions; rollback after revision, cases, request and event insertion; immutable-record write privileges; anon/authenticated direct table/function denial; missing owner authority; manifest/receipt byte tampering and recomputed approval-flag rejection; selected second-source rights denial on full-package operations; authority denial on retry/readback. The first positive check was observed failing against a function returning an empty result before implementation. The validation increment separately observed acceptance of a rehashed malformed receipt before the shape fix, then rejection afterward; missing history writers were observed before implementation.

The private schema revokes browser usage and function EXECUTE, enables RLS, and grants backend SELECT/INSERT only for immutable evidence records. Authority/source-policy fixtures are seeded/changed by the disposable administrator, never by the backend role. SECURITY INVOKER functions have empty search_path. Actor arguments are synthetic delegated server identities; this does not authenticate sessions or prove real account membership. Backend credentials remain trusted; unrelated browser users cannot call these RPCs.

This remains a disposable prototype of SOURCE_EVIDENCE_DATABASE_DESIGN.md. It now has an immutable package owner/lexical-ID row, revisions/cases/requests/events, and append-only versioned authority/source-policy history. Its private administrative writers use the same advisory transaction lock as staging/readback. Current checks select the latest history version, so an older allow cannot bypass a later deny. Backend/browser roles cannot invoke the authority writers; the disposable administrator seeds/transitions synthetic state. These are fixture governance roles, not real owner/session verification. Exact-revision metadata withdrawal and disposable snapshot recovery are now exercised below. Reviewer grants, erasure lifecycle, byte retention and production recovery are not implemented.

SQL independently validates exact package/case/appearance/interpretation shapes and scalar limits, distinct case IDs, binding fields, receipt keys/UUIDs/canonical millisecond UTC date strings and false approval flags. The same receipt invariants apply to staging, stored readback and exact retries. Readback binds canonical documents to actual package/revision/request rows and reconciles per-case projections; raw-inserted inconsistent records are rejected. Negative tests include rehashed malformed receipts, forged claims/manifests/request fingerprints, corrupted case projections and mismatched physical package keys.

`digests.sql` implements domain_canonical/domain_hash only for ASCII printable strings/keys and integers 0..1e9, plus boolean/null/array/object structure. It explicitly rejects Unicode/control strings, negative/fractional/out-of-range numbers. It is **not a general RFC8785 serializer**. Valid evidence labels/locators, UUIDs, timestamps, hashes and profile literals fit this restricted domain. ASCII C-order key sorting and integer serialization are compared to the existing JavaScript canonicalizer. Twelve oracle packages exercise all six relations, four rotations, null/proposed identity, mixed sources and integer boundaries. Helper serializer quoting/backslash and numeric-scale cases also match JavaScript; unsupported-domain cases reject.

SQL independently constructs appearance/case hashes, sorted package manifest/profile, sorted claimsDigest, request fingerprint and receipt checksum. Canonical byte comparison rejects whitespace, reordered object keys or duplicate-key spellings rather than silently hashing JSONB::text. Case-array order is normalized only for stored package snapshots/digests, allowing a reversed-order exact retry to return the original receipt. Stage requires schema validation before digest derivation; readback recomputes from stored canonical documents. Existing JavaScript validation remains mandatory at the eventual adapter boundary. This is tested restricted-domain parity, not general JCS certification or exhaustive cross-engine equivalence.

The private writers serialize inside the embedded instance. Disposable tests cover postcommit status handling, stored readback corruption, transaction-driver conformance and recovery of the prototype. The native fixture section below now verifies independent-connection races. Hosted Auth, network/crash durability and full production export/restore acceptance remain unverified. Existing production authority writers are unrelated to these fixture functions and have not been integrated. A new allowed policy event is an explicit administrative fixture transition, not automatic access restoration by retry. History cannot be updated/deleted, even by the disposable administrator through ordinary SQL; the admin remains trusted for new append events and platform DDL.

Fault injection is intentionally callable only in this disposable fixture and must never enter a production API. SQL returns committed, not accepted. No hosted migration, real grant/source upload, production RLS/Auth assurance or learner publication follows.

The disposable driver below now runs the existing transaction conformance harness against SQL records. Keep hosted migrations/API wiring/reviewer grants/source bytes disabled until remaining authorization, concurrency and recovery requirements pass.

Primary references consulted for this increment: [RFC8785](https://www.rfc-editor.org/rfc/rfc8785) and [PostgreSQL JSON functions](https://www.postgresql.org/docs/current/functions-json.html). No new SQL extension/service is introduced.

## SQL transaction conformance driver

Run the reusable transaction harness against real disposable SQL tables/functions:

```sh
PGLITE_MODULE_URL=file:///absolute/scratch/tooling/node_modules/@electric-sql/pglite/dist/index.js node scripts/source-evidence-sql-conformance.js
```

`scripts/lib/source-evidence-sql-driver.js` creates/closes a fresh in-memory database per scenario. It captures and validates the candidate before asynchronous work, recomputes the canonical envelope, stages through SQL and returns accepted only after a separate protected SQL readback plus independent JavaScript package/receipt checks. `inspect()` queries committed revisions, requests and events; it does not keep a parallel success-state mirror. The harness independently rehashes inspected claims and checks request/receipt bindings. Inspection projects the fixed lower-case UUID fixtures used by this harness; it is not a generic export or client endpoint.

The driver passes all ten existing scenarios: exact retry, request/revision conflicts, atomic precommit failure, lost acknowledgement, unavailable/tampered readback, overlapping identical/conflicting calls and authority recheck. Three deliberately broken wrappers must be rejected: accepting uncertain outcomes, accepting corrupted readback and reporting inconsistent stored claims. Each wrapper closes its database through the harness finally block.

Fault distinctions matter: before-commit injects an actual SQL exception after case insertion and verifies no committed revision/request/event; the standalone SQL probe separately checks four write-boundary rollbacks, including package records. After-commit and readback-unavailable simulate failed delivery after a successful SQL statement, rather than killing a server or demonstrating a real network outage. Readback-tampered alters the returned candidate projection, not the stored SQL records; retry reads unchanged records. These deterministic faults prove driver's fail-closed status/receipt handling, not crash durability.

A promise queue serializes this driver's single embedded connection, including the privileged fixture deny writer. Overlapping Promise.all calls therefore test request convergence through this driver, not independent PostgreSQL connection locking or a production revoke race. No hosted Auth session, production authority path, production backup/restore, deployed adapter, source bytes or reviewer grant is added. Unknown SQL outcomes return uncertain; integrity/denial results expose no receipt. Malformed pre-SQL candidates return invalid without writes. The fixture administrative role never escapes through its public driver surface; its controls only perform fixed synthetic governance and recovery instrumentation.

Withdrawal, postcommit current denial and disposable recovery checks are implemented below. Native fixture multi-connection acceptance is recorded below; hosted authorization acceptance is still required before adapter/API consideration. These are private prototypes, not production migration candidates.

Lifecycle regression checks start staging and immediately close the driver, including two concurrent close callers. Preparation/hashing, SQL and readback all belong to the tracked queue; close waits for the entire in-flight operation, and repeated close calls share its completion. New staging after close rejects. These paths were observed failing before their fixes.


## Withdrawal, postcommit denial and disposable recovery

Run scripts/source-evidence-recovery-check.js with the same PGLITE_MODULE_URL command prefix. It verifies three linked slices:

1. The exact package/version/digest can receive one immutable withdrawal record. Wrong digests/owners are denied; repeat withdrawal is idempotent. Common stage/readback guards deny the withdrawn revision without rewriting evidence/receipts. Another version is a distinct target; withdrawal is not a package-wide deletion or source-byte retention decision.
2. Test-only account, source-policy or withdrawal changes can be injected after actual SQL commit and before protected readback. The readback then returns denied and no receipt; committed audit records remain and retries cannot revive access. These schedules are deterministic in one connection, not real parallel revocation races.
3. A privileged disposable snapshot includes all eight prototype tables: authority, source_policy, packages, revisions, cases, requests, events and withdrawals. Export uses a repeatable-read transaction and shared lock. Its digest identifies the exact table payload bytes. It is an in-memory synthetic recovery fixture, not a production backup or export endpoint.

Restore requires a separately retained expected snapshot digest. Changing both data and its attached checksum does not bypass that external comparison. A digest is not origin authentication: trusting an attacker-selected expected digest cannot prove complete history. Restore creates a fresh isolated database, imports in one transaction, and skips all fixture allow-seeding. It audits canonical manifests/cases/requests/receipts, exact physical identity/owner links, case projections, complete contiguous policy/authority histories, request/event links and withdrawals, without using a current-access read to validate historical denied data. Histories present in the snapshot stay denied; later external revocations after capture still require reconciliation before any real release.

Target tables must be empty. Unknown/missing table keys, changed checksum/pin, malformed rows or internal binding corruption reject. Import failure rolls back every table; no existing target is overwritten. Event IDs/bindings are non-null and event rows uniquely bind requests; identity state is advanced after import. Opaque SQL JSON table payload strings preserve integer values without JavaScript parsing/rounding of database sequence IDs. The bounded envelope limit is 64 MiB. No arbitrary schema/table names, SQL URLs or file paths are accepted by the helper.

Tests restore allowed, account-denied, policy-denied and withdrawn fixtures; preserve original receipts/history and browser denial; exercise postrestore writes; reject rehashed corrupt claims, missing authority history and orphan audit events; prove partial-import rollback and nonempty-target refusal. Snapshot bytes remain unchanged when the source later accepts another revision. Backend/browser roles cannot invoke the private SQL withdrawal/governance writers; driver controls are privileged synthetic test instrumentation, not user-facing APIs.

The restore fixture reconstructs prototype DDL/ACLs/roles from checked-in SQL. It does not migrate real Auth, secrets, external objects, deleted content, real reviewers or production rights. No snapshot is written to disk or committed; only synthetic check code is saved. Native fixture independent-connection checks are recorded below. Remaining work: current production authority/session integration, production-consistent export inventory/restore acceptance, crash recovery and rights/reviewer gates before any hosted migration or API.

## Native independent-connection acceptance

scripts/source-evidence-pg-concurrency.js starts its own native PostgreSQL cluster, with TCP disabled and a private Unix socket. No hosted URL/configuration is accepted. Three separate client/backend PIDs execute checked-in fixture SQL. Actual pg_locks waiters and pg_blocking_pids establish ordering; Promise overlap alone is not accepted as evidence.

Scenarios cover exact retry convergence, conflicting payloads, withdrawal-first and stage-first ordering, authority/policy denial after lock waits, and an outer transaction rollback releasing a waiter. A separate fresh native database restores the eight-table snapshot and compares its exact digest, receipts, withdrawal denial and browser ACLs. The --omit-locks option modifies fixture SQL only in memory; it must fail specifically with advisory_barrier_not_observed while still completing cleanup.

The existing Foundation CI now has an isolated evidence-native-postgres job on Ubuntu24.04 with Node24, @embedded-postgres/linux-x6418.6.0-beta.19 (PostgreSQL18.6 binary) and pg8.22.0 installed outside the app. It runs the positive check and verifies the expected negative-control failure/cleanup. No credentials, hosted database, production schema, application dependency or source corpus is involved.

Local root-only namespace mapping prevents launching PostgreSQL as an unprivileged account: chown to nobody fails EINVAL, and a user-namespace attempt was denied. The helper reports native_postgres_requires_non_root_runner and removes its temporary copy; it does not bypass PostgreSQL root checks or create OS users. Non-root runners use their own identity; root runners require an existing mapped uid65534. CI execution is the required native result; local PGlite passes must not substitute for it.

For a suitable non-root Linux host, install pinned verification packages in temporary tooling, set NATIVE_PG_MODULE_URL to the binary package dist/index.js file URL and PG_MODULE_URL to pg/esm/index.mjs, then run the script. The helper copies only its supplied native toolchain into its own private temporary directory, starts a private server and closes clients/stops the server/removes that directory in finally. This tests the disposable schema's locks/roles/recovery; it is not hosted Supabase Auth/RLS/current production authority acceptance or a crash-durability certificate.

## Immediate-shutdown/WAL recovery acceptance

scripts/source-evidence-pg-crash-recovery.js uses the same private native cluster helper. It asserts fsync, synchronous_commit and full_page_writes are on, stages acknowledged and simulated-lost-delivery commits, persists metadata withdrawal/source-policy/account denial, and leaves a separate transaction uncommitted. The restart hook uses pg_ctl immediate shutdown, waits for the server to stop, then starts the same data directory and waits for its ready log. It does not kill arbitrary processes or bypass PostgreSQL root restrictions.

Acceptance requires a changed postmaster PID and explicit interrupted/automatic-recovery log evidence. The committed eight-table payload digest must survive exactly, the uncommitted package/cases/request/event must be absent, accepted/lost-delivery retries must return original receipts, denied records must remain denied, and a fresh postcrash native restore must retain receipt/history/ACL parity. Client error events are expected during immediate shutdown; all old and new clients are closed in cleanup.

This is process-crash/WAL replay acceptance, not a hardware/OS power-loss, disk-controller or production replication certificate. Simulated lost application delivery is not an actual network interruption. No real Auth sessions or hosted tables are used. The initial native test-first checkpoint95b2378 failed at the expected missing-hook assertion in run41171677157/job124450852230 and still confirmed cleanup; the successful implementation verification is recorded below.

[WAL reliability](https://www.postgresql.org/docs/current/wal-reliability.html) explains storage/hardware limits beyond this fixture.

Four actual helper behavior tests use synthetic tokens/RPC fixtures and do not certify live Auth.
